# 展示截图与演示顺序

截图来自实际运行的试剑 V3，使用隔离的本地数据库与内置靶场，账号显示为 `demo_reviewer`。没有替换 DOM 统计值、伪造结果或使用设计稿冒充页面。

| 图片 | 场景与数据口径 |
|---|---|
| projects.png | 3 个独立演示项目：权限/状态、Schema、故障演练 |
| project-cases.png | 13 条专题用例中按“权限”标签筛出的 6 条 |
| coverage.png | 真实 OpenAPI 的 14 个端点，10 个已有保存用例；另有 1 条保存的 UI 冒烟用例，因此总用例为 11。最新执行只包含 10 条 API，用例全部通过，不表示未执行的 UI 也通过 |
| run-report.png | 主动调用 `/api/error/503`，预期 200；报告正确显示 1 失败、3 通过。这是有意注入的演示故障，不是正式业务缺陷 |
| workflow-report.png | 登录、创建、todo → doing → done → archived，展开末步的请求、响应和两项断言 |

Schema 早期执行使用尚未补齐参数的候选用例，失败记录保留；后续补充演示认证、有效资源 ID、请求体并明确上传缺文件的 422 负向预期，才执行最终 10 条回归。图表按旧到新展示真实结果，不能将这段参数准备过程解释为修复了 9 个产品 Bug。

推荐先看覆盖缺口，再展示权限用例的测试设计，进入 Workflow 逐步证据；最后展示 503 故障报告和执行快照。真实的产品缺陷修复闭环请看 [权限与状态专题](PERMISSION-STATE-TOPIC.md)，其中有独立的基线失败、根因、修复与复测记录。

本地演示数据库、登录凭据、原始日志和材料包均未提交。截图可用于介绍产品；其中统计只描述对应演示项目，不代表全平台覆盖率或生产可用性承诺。
